\chapter{Hiện thực và triển khai}
\label{chap:hien-thuc-trien-khai}

Chương này trình bày các quyết định hiện thực cụ thể bám theo thiết kế
ở Chương~\ref{chap:phan-tich-thiet-ke}: phiên bản công nghệ, cấu trúc

là cho phép một thành viên mới onboard có thể dựng lại toàn bộ stack
trên máy cá nhân hoặc VPS pilot trong dưới 1 giờ, đồng thời cung cấp
checklist phần cứng để giảng viên hướng dẫn ước lượng tài nguyên cần
chuẩn bị cho giai đoạn pilot.

\subsection{Hệ điều hành mục tiêu}

\textbf{Tầng pilot:} \textbf{Ubuntu Server 22.04 LTS} (Jammy Jellyfish)
là OS mục tiêu chính, được chọn vì:

\begin{itemize}
    \item Được Canonical hỗ trợ đến tháng 4/2027 (LTS 5 năm) và mở rộng
          ESM đến 2032, đủ dài cho vòng đời pilot và pha production
          tiếp theo của đồ án.
    \item Sẵn có các package cập nhật cho Docker Engine, Nvidia driver
          và các runtime cần thiết qua APT chính thức hoặc Docker/Nvidia
          official repository, không cần build từ source.
    \item Tương thích với \texttt{nvidia-container-toolkit}, cho phép
          \texttt{video-worker} truy cập GPU qua Docker Compose mà
          không cần can thiệp kernel module thủ công.
\end{itemize}

Tùy chọn dự phòng \textit{Ubuntu Server 24.04 LTS} (Noble Numbat) được
dùng nếu yêu cầu kernel mới hơn (vd. driver GPU thế hệ Blackwell) hoặc
PostgreSQL 17 native cho hàm \texttt{uuidv7()} built-in.

\textbf{Tầng dev:} không bắt buộc Linux để mở rộng khả năng tham gia
của thành viên. Các môi trường được hỗ trợ:

\begin{itemize}
    \item \textbf{macOS 14+ (Sonoma) hoặc 15+ (Sequoia):} Docker
          Desktop 4.28+; phù hợp Apple Silicon (M1/M2/M3) nhờ image
          multi-arch (\texttt{linux/arm64}) của các base image trong
          stack. Whisper local có thể chạy qua Metal Performance Shaders.
    \item \textbf{Windows 11 + WSL2 (Ubuntu 22.04):} Docker Desktop
          backend WSL2; source code mount trong WSL2 file system để
          tránh latency I/O cross-OS.
    \item \textbf{Linux Desktop (Ubuntu 22.04/24.04, Fedora 40+):}
          Docker Engine native, không qua VM, performance tốt nhất cho
          dev có GPU.
\end{itemize}

\textbf{Tầng ci:} GitHub Actions runner mặc định
\texttt{ubuntu-22.04} (chuyển sang \texttt{ubuntu-24.04} sau tháng
4/2025 khi GitHub đổi default).

\subsection{Yêu cầu mạng và tên miền}
\label{subsec:network-req}

\begin{itemize}
    \item \textbf{Inbound:} cổng 443/tcp public cho LTI launch từ
          Canvas và truy cập của giảng viên/học viên. Cổng 80 chỉ
          redirect 301 sang HTTPS, không phục vụ traffic thực.
    \item \textbf{Outbound:} cổng 443/tcp đến: Canvas (LTI AGS
          callback, JWKS), Gemini API
          (\texttt{generativelanguage.googleapis.com}), provider STT
          fallback (OpenAI/AssemblyAI nếu cấu hình).
    \item \textbf{Docker network nội bộ:} \texttt{ai\_internal} bridge,
          \textit{không expose port của container database ra host}
          trong production. Chỉ \texttt{caddy} bind vào host network.
    \item \textbf{Tên miền:} cần một subdomain với chứng chỉ SSL hợp
          lệ (Let's Encrypt qua Caddy tự động), vd.
          \texttt{lvtn-ai.example.edu.vn}. Canvas chỉ chấp nhận LTI
          Tool có HTTPS hợp lệ, không dùng được self-signed certificate.
\end{itemize}

\section{Cấu trúc mã nguồn}
\label{sec:code-structure}

\subsection{Tổ chức monorepo}

Mã nguồn được tổ chức dưới dạng monorepo với pnpm workspace cho
TypeScript và Poetry workspace cho Python, sống chung trong một
repository để dễ refactor cross-language khi sửa contract gRPC hoặc
event schema:

\begin{verbatim}
lvtn-ai/
|-- apps/
|   |-- web-bff/                # Next.js 14, App Router
|   |-- core-api/               # NestJS, business logic
|   |-- chat-service/           # FastAPI, RAG + SSE
|   |-- document-worker/        # Python + BullMQ
|   |-- enrichment-worker/      # Python + BullMQ
|   `-- video-worker/           # Go + FFmpeg + Whisper
|-- packages/
|   |-- shared-contracts/       # Protobuf, OpenAPI, Zod schema
|   |-- shared-domain-py/       # Python: Hexagonal Port (ABC)
|   |-- shared-domain-ts/       # TypeScript: domain entity, DTO
|   `-- shared-eslint-config/
|-- infra/
|   |-- docker-compose.yml      # Stack pilot
|   |-- docker-compose.dev.yml  # Override cho dev
|   |-- caddy/Caddyfile
|   |-- prometheus/prometheus.yml
|   |-- grafana/dashboards/
|   |-- postgres/migrations/    # Atlas hoặc Liquibase
|   `-- neo4j/cypher-init/
|-- tools/
|   |-- seed-data/
|   |-- eval-retrieval/         # Recall@K, MRR script
|   `-- benchmark/
|-- docs/
|   |-- ARCHITECTURE.md
|   |-- RUNBOOK.md
|   `-- ONBOARDING.md
|-- .github/workflows/          # CI/CD pipeline
|-- pnpm-workspace.yaml
|-- pyproject.toml              # Root Poetry
`-- README.md
\end{verbatim}

Lý do chọn monorepo thay vì polyrepo: contract giữa các runtime (event
schema BullMQ, gRPC proto, JWT claim shape) thay đổi đồng thời với
implementation; nếu tách repo thì mỗi lần sửa schema phải tạo PR ở
nhiều nơi và lock version chéo. Với monorepo, một PR thay đổi cả
producer và consumer của cùng một sự kiện, CI chạy integration test
toàn cục.

\subsection{Layout Hexagonal trong worker Python}

Mỗi worker Python (\texttt{document-worker}, \texttt{enrichment-worker},
\texttt{chat-service}) tuân thủ cùng một layout Hexagonal:

\begin{verbatim}
apps/document-worker/src/document_worker/
|-- domain/                # Entity, Value Object, Port (ABC)
|   |-- entities/
|   |   |-- document.py
|   |   `-- chunk.py
|   |-- ports/
|   |   |-- parser_port.py        # IParser
|   |   |-- embedding_port.py     # IEmbeddingModel
|   |   |-- vector_store_port.py  # IVectorStore
|   |   `-- metadata_store_port.py
|   `-- exceptions.py
|-- application/           # Use case, orchestration
|   |-- use_cases/
|   |   |-- process_document.py
|   |   `-- reindex_document.py
|   `-- dto.py
|-- infrastructure/        # Adapter implementations
|   |-- adapters/
|   |   |-- pymupdf_parser.py     # IParser -> PyMuPDF
|   |   |-- docling_parser.py     # IParser -> Docling (OCR)
|   |   |-- bge_m3_local.py       # IEmbeddingModel -> local
|   |   |-- openai_embedding.py   # IEmbeddingModel -> API
|   |   |-- qdrant_store.py       # IVectorStore -> Qdrant
|   |   `-- postgres_metadata.py
|   `-- config.py
|-- delivery/              # Primary adapter
|   |-- bullmq_consumer.py
|   `-- grpc_server.py
`-- main.py                # Dependency injection bootstrap
\end{verbatim}

Quy ước phụ thuộc: \texttt{domain} không import gì từ
\texttt{application}/\texttt{infrastructure}/\texttt{delivery};
\texttt{application} chỉ import từ \texttt{domain};
\texttt{infrastructure} và \texttt{delivery} có thể import cả
\texttt{domain} và \texttt{application}. Quy tắc này được enforce
bằng \texttt{import-linter} trong CI.

\subsection{Quy ước commit và branching}

\begin{itemize}
    \item \textbf{Conventional Commits} với scope per runtime:
          \texttt{feat(chat-service): ...},
          \texttt{fix(document-worker): ...},
          \texttt{chore(infra): ...}.
    \item \textbf{Trunk-based development:} branch ngắn (1--3 ngày),
          merge vào \texttt{main} qua PR có review.
    \item \textbf{Tag release:} \texttt{v1.0-pilot-w7},
          \texttt{v1.0-defense} ở mốc quan trọng để có thể rollback
          nếu pilot lỗi.
\end{itemize}

\subsection{\texttt{web-bff} (Next.js)}

Frontend kiêm Backend-for-Frontend được hiện thực bằng Next.js 14 với
App Router. Ba vai trò chính:

\begin{itemize}
    \item Render UI server-side cho giảng viên (\texttt{/manage/*})
          và học viên (\texttt{/learn/*}).
    \item Tiếp nhận LTI launch và phát hành phiên qua cookie
          \texttt{HttpOnly}, \texttt{SameSite=None}, \texttt{Secure}
          (bắt buộc do chạy trong iframe Canvas).
    \item Proxy request từ UI sang \texttt{core-api} và
          \texttt{chat-service}, kèm BFF-to-Core JWT ngắn hạn.
\end{itemize}

Cấu trúc route chính (App Router):

\begin{itemize}
    \item \texttt{app/lti/login/route.ts}: OIDC login init, lưu
          \texttt{state} + \texttt{nonce} vào Redis (TTL 5 phút), redirect
          về Canvas authorize endpoint.
    \item \texttt{app/lti/launch/route.ts}: nhận form POST, verify JWT
          \texttt{id\_token} qua Canvas JWKS, ánh xạ user, set cookie
          phiên, redirect theo role.
    \item \texttt{app/manage/review/page.tsx}: review inbox, list card/quiz
          draft, action approve/reject/edit.
    \item \texttt{app/manage/documents/page.tsx}: upload + danh sách tài liệu.
    \item \texttt{app/learn/lessons/[id]/page.tsx}: card view + nav.
    \item \texttt{app/learn/lessons/[id]/quiz/page.tsx}: làm quiz.
    \item \texttt{app/learn/chat/page.tsx}: AI Tutor chatbot.
    \item \texttt{app/api/sse-chat/route.ts}: proxy SSE từ
          \texttt{chat-service} về browser, không buffer.
\end{itemize}

Session LTI lưu phía server (Redis) thay vì cookie để giảm rủi ro lộ
claim nhạy cảm và để có thể vô hiệu hoá tức thì khi logout. Frontend
không tự quyết định phân quyền nghiệp vụ; mọi quyết định authorize
chuyển về \texttt{core-api} qua JWT.

\subsection{\texttt{core-api} (NestJS)}

\texttt{core-api} hiện thực bằng NestJS 10 với Fastify adapter để
giảm overhead so với Express, đóng vai trò trung tâm nghiệp vụ:

\begin{itemize}
    \item Quản lý metadata: \texttt{documents}, \texttt{videos},
          \texttt{lesson\_cards}, \texttt{quiz\_items}, \texttt{courses}.
    \item Phân quyền: kiểm tra role \texttt{Instructor}/\texttt{Learner}
          theo course context trích từ JWT.
    \item Review/Publish: state machine của card/quiz, ghi audit log.
    \item Điều phối job: publish event vào BullMQ (gọi qua HTTP
          \texttt{BullMQ Pro} hoặc trực tiếp Redis client).
    \item Chứa Outbox Poller daemon chạy in-process.
\end{itemize}

Module structure (NestJS): mỗi bounded context một module
(\texttt{CourseModule}, \texttt{DocumentModule}, \texttt{ContentModule},
\texttt{ReviewModule}, \texttt{AnalyticsModule}, \texttt{OutboxModule}),
mỗi module có
\texttt{*.controller.ts}/\texttt{*.service.ts}/\texttt{*.repository.ts}/\texttt{*.dto.ts}.

ORM: Prisma cho query và migration; lý do chọn Prisma thay vì TypeORM:
generated type-safe client, schema khai báo single source, có CLI
migrate tốt cho team.

\subsection{\texttt{chat-service} (FastAPI)}

\texttt{chat-service} hiện thực bằng FastAPI 0.110+ với Uvicorn (2
worker process, không dùng Gunicorn để giữ async event loop). Hai
endpoint chính:

\begin{itemize}
    \item \texttt{POST /chat/ticket}: cấp Single-Use Ticket cho client
          mở SSE. Verify JWT BFF-to-Core, sinh ticket UUID lưu Redis
          TTL 60s.
    \item \texttt{GET /chat/stream?ticket=...\&q=...}: kiểm tra ticket,
          consume ticket (chỉ dùng được 1 lần), thực thi RAG, stream
          token qua \texttt{StreamingResponse} với MIME
          \texttt{text/event-stream}.
\end{itemize}

Internal pipeline trong \texttt{stream}:

\begin{enumerate}
    \item Sinh dense+sparse embedding bằng BGE-M3.
    \item Search Qdrant hybrid với filter cứng \texttt{course\_id}.
    \item Reciprocal Rank Fusion.
    \item Query Neo4j lấy LO context (graph-aware reranking).
    \item Build prompt + gọi Gemini Pro streaming.
    \item Yield từng token kèm citation marker.
    \item Persist \texttt{chat\_messages} vào PostgreSQL sau khi
          stream xong.
\end{enumerate}

\subsection{\texttt{document-worker}}

\texttt{document-worker} hiện thực bằng Python 3.11 + BullMQ Python
client (\texttt{bullmq-python}). Container có ba vai trò chính trong
cùng tiến trình:

\begin{itemize}
    \item \textbf{Document processing consumer:} tải file từ MinIO,
          parse (PyMuPDF cho text layer, Docling cho OCR), chunk theo
          heading, embed bằng BGE-M3, upsert Qdrant.
    \item \textbf{Graph sync consumer:} consume sự kiện Outbox từ
          PostgreSQL (chuyển tiếp bởi \texttt{core-api}) để tạo node
          và relationship trong Neo4j qua Cypher \texttt{MERGE}.
    \item \textbf{Curriculum ingestion consumer:} consume
          \texttt{CurriculumIngestionRequested}, dùng Gemini Flash
          parse DCMH PDF thành Course/Chapter/LO/Assessment.
\end{itemize}

\texttt{BGE-M3} được load lazy ở lần job đầu tiên (giảm 10--15 giây
startup nếu container restart liên tục) và giữ trong RAM cho mọi job
sau. Mỗi job dùng Hexagonal use case
\texttt{ProcessDocumentUseCase.execute(document\_id)} để cô lập logic
khỏi framework BullMQ --- giúp test unit không cần spin up Redis.

\subsection{\texttt{enrichment-worker}}

\texttt{enrichment-worker} consume sự kiện
\texttt{ContentGenerationRequested} (type=card hoặc quiz), gom chunk
theo heading cấp 2 hoặc theo LO, build prompt với JSON schema strict,
gọi Gemini Pro/Flash, validate output, persist artifact ở status
\texttt{GENERATED\_DRAFT}.

Đặc tính I/O-bound: mỗi LLM call có thể tốn 5--30 giây. Worker được
cấu hình \texttt{concurrency=10} (10 job đồng thời) thay vì 1 như các
worker CPU-bound. Khi gặp HTTP 429 (rate limit) từ Gemini, BullMQ
exponential backoff retry 3 lần ($1s \to 2s \to 4s$); sau đó chuyển
sang fallback model (Gemini Flash thay vì Pro) và retry thêm 1 lần.

\subsection{\texttt{video-worker} (Go)}

\texttt{video-worker} hiện thực bằng Go 1.22+ thay vì Python để: (i)
tránh GIL khi điều phối FFmpeg subprocess song song qua goroutine,
(ii) build static binary nhỏ ($\approx$ 20MB) so với image Python
($\approx$ 1GB), (iii) handle stream lớn ổn định hơn với
\texttt{io.Pipe} của Go.

Pipeline mỗi job:

\begin{enumerate}
    \item Download video từ MinIO qua presigned URL stream (không tải
          hết vào RAM).
    \item \texttt{ffmpeg -i input.mp4 -vn -acodec pcm\_s16le -ar 16000}
          để extract audio mono 16kHz cho Whisper.
    \item Gọi Whisper qua \texttt{whisper.cpp} binding (cho local) hoặc
          HTTP API (cho fallback). Output là transcript có timestamp
          từng word.
    \item Detect segment boundary: silence $\geq 1.5s$ + topic shift
          (cosine similarity giữa các đoạn embedding $< 0.7$).
    \item Cắt clip 30--90 giây bằng \texttt{ffmpeg -ss ... -t ... -c
          copy} (không re-encode).
    \item Upload clip về MinIO, insert
          \texttt{video\_segments}/\texttt{transcript\_segments} vào
          PostgreSQL.
    \item Publish \texttt{TranscriptReady} cho
          \texttt{document-worker} embed.
\end{enumerate}

Vì thời gian xử lý 1 video 60' có thể vượt 30 phút --- ngưỡng stalled
job mặc định của BullMQ --- worker gọi \texttt{job.updateProgress()}
mỗi 10 giây để xác nhận tiến độ.

\subsection{Outbox poller daemon}

Outbox Poller chạy in-process trong \texttt{core-api} (NestJS module
\texttt{OutboxModule}) với cron \texttt{*/5 * * * * *} (mỗi 5 giây):

\begin{enumerate}
    \item Query \texttt{outbox\_events WHERE status='PENDING' ORDER BY
          occurred\_at LIMIT 100 FOR UPDATE SKIP LOCKED}.
    \item Mỗi event được chuyển thành BullMQ job với
          \texttt{jobId = outbox\_id} (idempotent).
    \item Khi BullMQ \texttt{add()} thành công, update
          \texttt{status='PROCESSED'}, ghi
          \texttt{processed\_at}.
    \item Nếu \texttt{add()} fail, để \texttt{status='PENDING'}, tăng
          \texttt{retry\_count}, sau 5 lần chuyển
          \texttt{status='FAILED'} và ghi \texttt{last\_error}.
\end{enumerate}

\subsection{Retry policy và Dead Letter Queue}

BullMQ cấu hình mỗi queue:

\begin{itemize}
    \item \texttt{attempts=3}, \texttt{backoff={type:'exponential',
          delay:1000}} $\to$ retry sau 1s, 2s, 4s.
    \item Sau khi vượt \texttt{attempts}, job chuyển sang
          \texttt{failed} list của BullMQ. Có một queue dashboard
          (\texttt{bull-board} hoặc Arena) để engineer requeue thủ
          công.
    \item Job lỗi do file corrupt được tag
          \texttt{discardOnError=true} để không retry phí token LLM.
\end{itemize}

\subsection{Idempotency cho consumer}

\begin{itemize}
    \item Chunk dùng UUIDv7 làm khoá chính; \texttt{INSERT ... ON
          CONFLICT (chunk\_id) DO UPDATE} để upsert.
    \item Qdrant upsert theo \texttt{chunk\_id} $\to$ tự lũy đẳng.
    \item Neo4j dùng \texttt{MERGE} thay vì \texttt{CREATE}.
    \item BullMQ \texttt{jobId} ràng buộc duy nhất theo
          \texttt{outbox\_id} $\to$ cùng một event không được enqueue 2
          lần.
\end{itemize}

\section{Tích hợp Canvas LMS qua LTI 1.3}
\label{sec:lti-impl}

\subsection{Cấu hình Developer Key trên Canvas}

Quy trình đăng ký Tool vào Canvas (Cloud sandbox cho dev/pilot):

\begin{enumerate}
    \item Tạo Developer Key dạng \textit{LTI Key} trong Canvas Admin.
    \item Cấu hình \texttt{Target Link URI} =
          \texttt{https://lvtn-ai.example/lti/launch},
          \texttt{OIDC Initiation URL} =
          \texttt{https://lvtn-ai.example/lti/login},
          \texttt{JWKS URL} = \texttt{https://lvtn-ai.example/.well-known/jwks.json}.
    \item Bật scope: \texttt{lineitem.readonly}, \texttt{lineitem},
          \texttt{score} (cho AGS), \texttt{result.readonly},
          \texttt{names\_and\_roles} (cho NRPS).
    \item Lấy \texttt{Client ID} và \texttt{Deployment ID} $\to$ lưu vào
          env của \texttt{web-bff}.
\end{enumerate}

\subsection{Endpoint OIDC login và launch}

Cấu trúc handler trong \texttt{web-bff}:

\begin{itemize}
    \item \texttt{/lti/login}: nhận \texttt{iss}, \texttt{login\_hint},
          \texttt{client\_id}, \texttt{target\_link\_uri}; sinh
          \texttt{state} và \texttt{nonce} cryptographic random; lưu
          Redis TTL 5 phút; redirect 302 đến
          \texttt{{iss}/api/lti/authorize\_redirect}.
    \item \texttt{/lti/launch}: nhận form POST có
          \texttt{id\_token} (JWT) và \texttt{state}; verify state
          khớp Redis, verify nonce chưa dùng, verify JWT signature qua
          Canvas JWKS (cache 24h), verify \texttt{aud}, \texttt{exp},
          \texttt{iss}; trích \texttt{sub} (LMS user ID),
          \texttt{context.id} (course ID), \texttt{roles}; upsert
          \texttt{lms\_user\_mappings} qua \texttt{core-api}; set
          cookie session.
\end{itemize}

\subsection{BFF-to-Core JWT signing}

\texttt{web-bff} có một cặp khóa Ed25519 sinh ở bootstrap. Mỗi request
proxy sang \texttt{core-api} hoặc \texttt{chat-service} mang JWT mới
TTL 60s với claim:

\begin{itemize}
    \item \texttt{sub}: internal user ID (UUID).
    \item \texttt{course\_id}: course đang launch.
    \item \texttt{roles}: \texttt{Instructor}/\texttt{Learner}.
    \item \texttt{jti}: random UUID chống replay.
    \item \texttt{exp}, \texttt{iat}.
\end{itemize}

\texttt{core-api} và \texttt{chat-service} verify JWT qua public key
của BFF (load từ ConfigMap hoặc env). Public key có thể rotate khi
cần.

\subsection{Assignment and Grade Services (AGS)}

Khi học viên submit quiz xong, \texttt{core-api} chấm điểm và gọi AGS
passback:

\begin{enumerate}
    \item Xin OAuth 2.0 access token từ Canvas (\texttt{client\_credentials}
          grant với private key JWT assertion).
    \item POST đến \texttt{lineitems/{id}/scores} với payload
          \texttt{{userId, scoreGiven, scoreMaximum, activityProgress,
          gradingProgress}}.
    \item Cache token TTL 50 phút (token Canvas TTL 1 giờ).
\end{enumerate}

\subsection{Deep Linking (cho instructor placement)}

Giảng viên có thể chọn lesson cụ thể để gắn vào activity Canvas qua
Deep Linking 2.0:

\begin{itemize}
    \item Canvas redirect đến \texttt{/lti/deep-link-select} với
          \texttt{deep\_link\_return\_url}.
    \item Giảng viên chọn lesson từ UI, BFF sinh
          \texttt{LtiResourceLinkRequest} JWT và POST về
          \texttt{deep\_link\_return\_url}.
    \item Canvas tạo activity với \texttt{custom.lesson\_id} được
          embed trong launch context tiếp theo.
\end{itemize}

\section{Đóng gói Docker Compose}
\label{sec:docker-compose}

\subsection{Tổ chức compose file}

Stack được cấu hình qua 1 base file + 2 override:
\texttt{docker-compose.yml} (pilot base), \texttt{docker-compose.dev.yml}
(mount source code, expose port DB ra host) và
\texttt{docker-compose.gpu.yml} (bật GPU cho \texttt{video-worker} và
\texttt{document-worker}). Lệnh chạy theo từng cấu hình:

\begin{lstlisting}[language=bash, caption={Chạy stack theo cấu hình.}]
# Pilot without GPU
docker compose -f infra/docker-compose.yml up -d --build

# Pilot with GPU (gpu overlay file)
docker compose -f infra/docker-compose.yml \
  -f infra/docker-compose.gpu.yml up -d --build

# Dev hot-reload (overlay file dev)
docker compose -f infra/docker-compose.yml \
  -f infra/docker-compose.dev.yml up
\end{lstlisting}

\subsection{Network và volume}

\textbf{Network:}
\begin{itemize}
    \item \texttt{ai\_internal} (bridge): kết nối nội bộ tất cả
          service. Không expose ra host trong pilot.
    \item \texttt{public} (bridge): chỉ \texttt{caddy} bind cổng 80
          và 443 vào host network.
\end{itemize}

\textbf{Volume:}
\begin{itemize}
    \item \texttt{pgdata}: PostgreSQL data; backup hàng ngày qua
          \texttt{pg\_dump} cron.
    \item \texttt{minio-data}: object storage.
    \item \texttt{qdrant-storage}: vector data.
    \item \texttt{neo4j-data}: graph data.
    \item \texttt{redis-data}: AOF persistence.
    \item \texttt{models} (bind mount \texttt{./models} read-only):
          chứa BGE-M3 và Whisper model, share cho \texttt{document-worker}
          và \texttt{video-worker}; tránh tải lại khi rebuild image.
    \item \texttt{caddy-data}, \texttt{caddy-config}: chứng chỉ Let's
          Encrypt.
\end{itemize}

\subsection{Resource limits cho container}

Mỗi service khai báo \texttt{deploy.resources.limits} theo
Bảng~\ref{tab:ram-allocation}. Ví dụ snippet cho \texttt{document-worker}:

document-worker:

  deploy:
    resources:
      limits:
        cpus: '2.0'
        memory: 4G
      reservations:
        memory: 3G

            count: 1
            driver: nvidia
  environment:
    - EMBEDDING_PROVIDER=bge-m3-local
    - LLM_PROVIDER=gemini
\end{lstlisting}

\subsection{Healthcheck và restart policy}

Mọi service có healthcheck:

\begin{itemize}
    \item HTTP service (\texttt{web-bff}, \texttt{core-api},
          \texttt{chat-service}): \texttt{GET /health} mỗi 30s.
    \item Worker: gọi \texttt{redis-cli PING} hoặc tự expose port
          metrics Prometheus với endpoint \texttt{/healthz}.
    \item Database: dùng built-in healthcheck của image
          (\texttt{pg\_isready}, \texttt{redis-cli ping},
          \texttt{curl} qua Qdrant \texttt{/healthz}).
\end{itemize}

\texttt{restart: unless-stopped} cho mọi service trừ container
one-shot (migration runner).

          pilot tối thiểu 16GB (không GPU) đến 32GB (có GPU); tổng
          phân bổ container khoảng 20GB.
    \item \textbf{Cấu trúc mã nguồn:} monorepo pnpm + Poetry workspace
          với 6 app runtime và shared packages; mỗi worker Python theo
          layout Hexagonal nghiêm ngặt.
    \item \textbf{6 runtime:} \texttt{web-bff} (Next.js),
          \texttt{core-api} (NestJS), \texttt{chat-service} (FastAPI),
          \texttt{document-worker} và \texttt{enrichment-worker}
          (Python), \texttt{video-worker} (Go).
    \item \textbf{Adapter switchable theo env:} embedding
          (BGE-M3/OpenAI), STT (Whisper local/OpenAI/AssemblyAI), LLM
          (Gemini/OpenAI) --- cho phép chạy dev không cần GPU.
    \item \textbf{Outbox poller + BullMQ} đảm bảo eventual consistency
          giữa PostgreSQL, Qdrant, Neo4j và downstream worker.
    \item \textbf{Tích hợp Canvas LMS} qua LTI 1.3 OIDC, AGS grade
          passback và Deep Linking; BFF-to-Core JWT Ed25519 cô lập
          phiên Canvas khỏi service backend.
    \item \textbf{Docker Compose} với 3 file (base + dev override +
          gpu override) là cách đóng gói chính; Kubernetes là định
          hướng tương lai sau bảo vệ.
    \item \textbf{CI/CD:} GitHub Actions với 4 job song song (lint,
          test, integration, build); secret quản lý qua env file mode
          600 hoặc GitHub Actions Secrets.
\end{itemize}

Chương 6 tiếp theo trình bày phương pháp và kết quả đánh giá hệ thống
dựa trên dữ liệu pilot thu thập theo kế hoạch ở
mục~\ref{sec:plan-gd2} trong Chương~\ref{chap:ket-luan-huong-phat-trien}.
